# Пошаговая инструкция

## Этап 1. Подготовка вспомогательного сервера и DNS

Во время первоначальной настройки станции запросы к нескольким доменам Yandex Quasar направляются на компьютер в локальной сети. Сервер проекта отвечает на перехваченные HTTPS-запросы так, как требуется сценарию настройки, и в остальных предусмотренных случаях обращается к настоящему серверу. Для HTTPS используются сертификаты eMudhra, уже включённые в выбранную реализацию.

### Выбор реализации

Есть несколько реализаций стенда, в том числе [eQuasar](https://git.gay/iwakura/eQuasar) с производными вариантами и приложение [AliceBridge](https://github.com/Yandex-Station-Universal-Repo/AliceBridge_APP). В этом руководстве далее используется [lite-kit](https://github.com/krevetkqqq/lite-kit)

Важная оговорка о версии: инструкция привязана к состоянию lite-kit, проверенному **21 ноября 2026 года**, коммит `65ae15297e393e45e98137433f2984883d6bcb84` (`main`). В будущем проект может измениться: поведение сервера, список доменов, сертификаты и команды могут отличаться. Для воспроизводимости может понадобиться откатиться к актуальному на момент написания руководства коммиту:

```sh
# station-max
git clone https://github.com/krevetkqqq/lite-kit.git
cd lite-kit
git checkout 65ae15297e393e45e98137433f2984883d6bcb84
```

Перед запуском проверьте, что команда `git rev-parse HEAD` показывает тот же хеш. Не копируйте ключи и сертификаты в публичные репозитории и не распространяйте их отдельно от проекта.

### Подготовка компьютера

Для данной инструкции в целом подразумевается использование Linux, иногда будет даваться информация о воспроизведении на macOS. По README lite-kit для Linux нужны `dnsmasq`, `python3` с OpenSSL не ниже 1.1.1, `openssl` и `dig`; на macOS нужен `dnsmasq` (например, установленный через Homebrew), `python3`, `openssl` и `dig`. Скрипт занимает сетевые порты `53`, `80` и `443`; до запуска проверьте, что они свободны. На Linux/macOS запуск требует прав администратора и скрипт сам запросит `sudo`.

Компьютер с сервером и станция должны быть доступны друг другу в одной локальной сети. Используйте **LAN-IP компьютера**, доступный станции, а не адрес VPN, контейнера или внешнего интерфейса. Желательно закрепить этот адрес DHCP-резервацией, чтобы DNS-записи не устарели при смене адреса.

### Настройка DNS на роутере

Нужно направить домены, указанные lite-kit, на LAN-IP компьютера с сервером:

- `quasar.yandex.net`
- `quasar.yandex.ru`
- `scbh.yandex.net`

Варианты настройки, от наиболее локального воздействия к более широкому:

1. Если роутер поддерживает DNS-переопределения для отдельного клиента, задайте их только для станции.
2. Если OpenWrt или другой роутер позволяет добавлять локальные DNS-записи, добавьте перечисленные A-записи на IP сервера. Это предпочтительно для данного сценария и не меняет DNS для остальных устройств.
3. В крайнем случае временно задайте IP компьютера DNS-сервером для всей домашней сети через настройки роутера/DHCP. Тогда остальные клиенты тоже будут использовать этот DNS. Учитывайте это влияние и верните исходную настройку после процедуры.

### Подготовка образа прошивки

Гайд рассчитан на установку прошивки `5000000921`, в данный момент репозиторий рассчитан на работу только с этой версией. Архив с прошивкой предполагается найти самостоятельно, один и вариантов поискать в telegram чатах. Архив который использовался мною имеет `sha256sum` `8bb2df2f34ab09b81017b56c511e4fd32178cd30248f92a1c2fc0f389ae13eee`. Данная контрольная сумма просто информация о воспроизводимости руководства. Для иного образа нет гарайтий работоспособности, так и нет уверености, что именно этот образ является достоверным. 

Образ прошивки необходимо загрузить в директорию lite-kit, пример команд выполняемых из каталога lite-kit:

```sh
# station-max/lite-kit
mkdir -p firmware/yandexstation_2
cp path_to_firmware/5000000921.zip firmware/yandexstation_2/5000000921.zip
# удаление manifest, который идет в проекте и предназначен для другой станции
rm firmware/manifest.json
```

Важно не изменять имя архива, оставить именно это

### Запуск lite-kit

Из каталога lite-kit запустите:

```sh
# station-max/lite-kit
sudo ./start.sh
```

Скрипт определяет LAN-IP компьютера (при необходимости его можно передать через `LOCAL_IP`), запускает `dnsmasq` и HTTPS/HTTP-сервер на портах `53`, `80` и `443`. В текущей версии скрипт сообщает адрес компьютера, обслуживаемые DNS-имена и путь к `log/server.log`; DNS-запросы записываются в отдельный журнал. 

После запуска проверьте, что DNS для `quasar.yandex.net` возвращает LAN-IP компьютера и что процесс сервера работает.

При наличии утилиты `dig` можно проверить следующим образом:

```sh
# 192.168.1.1 - LAN-IP роутера, если у вас иной измените
dig +short @192.168.1.1 quasar.yandex.ru
# Ожидается вывод LAN-IP сервера
```

> Важное уточнение: в lite-kit сервер и DNS-процесс запускаются в фоне. Не закрывайте компьютер и не останавливайте эти процессы, пока идёт первоначальная настройка станции. Обычно логи пишутся в log/server.log, соответственно смотреть их в реальном времени можно с помощью

```sh
# station-max/lite-kit
tail -f log/server.log
```

### Завершение этапа

Когда дальнейшая инструкция явно укажет, что вспомогательный стенд больше не нужен, из каталога lite-kit выполните:

```sh
# station-max/lite-kit
sudo ./stop.sh
```

Скрипт останавливает сервер и `dnsmasq`. После этого удалите временные DNS-переопределения или верните прежнюю DNS-настройку роутера. Если использовалась общая настройка DNS через DHCP, восстановите её для всей сети. Не останавливайте стенд раньше: устройство может ещё обращаться к нему в ходе первоначальной настройки.

## Этап 2. Сброс станции и первоначальная настройка

Перед сбросом убедитесь, что вспомогательный сервер запущен, DNS для станции направлен на компьютер с lite-kit, а в `lite-kit/firmware/yandexstation_2/` лежит подготовленный архив `5000000921.zip`. Сброс удаляет пользовательскую настройку и может восстановить заводскую прошивку; не прерывайте его отключением питания.

1. Отключите питание станции.
2. Нажмите и удерживайте кнопку Алисы.
3. Не отпуская кнопку, снова подключите питание.
4. Дождитесь жёлтого свечения светового кольца, затем отпустите кнопку и дайте станции завершить сброс и загрузку.
5. Когда станция предложит настройку, добавьте её через приложение «Дом с Алисой» и подключите к локальной сети, в которой доступен lite-kit.
6. После завершения первоначальной настройки станция должна сама запросить и начать установку прошивки `5000000921`. Не отключайте питание и не останавливайте lite-kit, пока передача и установка не завершатся и станция не перезагрузится.

### Проверка результата

Следите за `lite-kit/log/server.log` (например, `tail -f log/server.log` из каталога lite-kit). Для этого этапа ожидаются записи о запросе `/check_updates`, предложении версии `5000000921`, успешной выдаче OTA-файла и последующих запросах станции после перезагрузки. В журналах также могут встречаться повторы и сетевые ошибки; оценивайте их по контексту, а не считайте любую строку `Exception` признаком неудачного обновления.

После того как станция загрузилась и ADB доступен, проверьте именно системную версию прошивки:

```sh
adb connect <IP-станции>:5555
adb shell getprop ro.build.display.id
```

Ожидаемый вывод для целевой сборки: `PPR1.180610.011.5000000921`. Если команда не подключается, сначала проверьте IP станции и доступность порта 5555; отсутствие ADB само по себе ещё не показывает, на каком этапе остановилось обновление — сопоставьте его с логом сервера.

Если передача прошивки не завершилась, в журнале есть явная ошибка lite-kit/OTA или станция не вернулась в сеть, не переходите к следующему этапу. Сохраните журнал и разберите, относится ли ошибка к стенду, сети или самой станции; не делайте вывод о неисправности lite-kit только по наличию предупреждений или обрывов соединений.

## Этап 3. OTA-lock

Пока OTA-lock не включён, станция периодически проверяет обновления и может установить более новую прошивку. Для неё не проверены ни смещение `0x291352c`, ни политика SELinux, поэтому на такой прошивке перестанут работать и `get-root.py`, и `rootd`. Этот этап фиксирует сборку; root для него не нужен.

UPD: По последним обсуждениям в сообществе есть вопросы к надежности такой блокировки обновлений. Возможно стоит пробовать другие пути, один из таких установка ограничений с помощью iptables. В будущем информация скорее всего появится в этом руководстве, но в данный момент ее нет. Лично у меня удаления пакета выходит достаточно, но риск не уходит. Потенциально может получиться, что станция сама по себе обновится. В целом это не страшно, но придется все процедуры повторять заново.

### 3.1. Включение OTA-lock

Проверьте, что пакет установлен:

```sh
adb -s 192.168.1.149:5555 shell pm list packages | grep com.yandex.launcher.updaterapp
```

Если вывод пуст, OTA-lock на этой сборке уже включён — переходите к 3.2. Иначе удалите пакет для пользователя 0:

```sh
adb -s 192.168.1.149:5555 shell pm uninstall --user 0 com.yandex.launcher.updaterapp
```

У ADB shell на этой прошивке есть `android.permission.DELETE_PACKAGES`, поэтому команда выполняется без root. Удаление для пользователя 0 сохраняется после перезагрузки. Проверьте, что пакет больше не числится установленным:

```sh
adb -s 192.168.1.149:5555 shell pm list packages | grep com.yandex.launcher.updaterapp
```

Пустой вывод означает, что пакет удалён для пользователя 0; файлы приложения остаются в `/system/priv-app/YandexUpdater`. Снять OTA-lock можно так:

```sh
adb -s 192.168.1.149:5555 shell pm install-existing --user 0 com.yandex.launcher.updaterapp
```

### 3.2. Выключение lite-kit

ADB на станции включается через lite-kit: при синхронизации станция получает конфигурацию `system_config.adbd`. После остановки стенда первая же перезагрузка закроет ADB, если на станции ещё не установлен `adbd-watchdog` (он появляется на Этапе 4). Поэтому:

- рекомендуется отложить выключение lite-kit до конца Этапа 4;
- если выключаете сейчас, не перезагружайте станцию, пока не установите `rootd` с `adbd-watchdog`.

Остановка стенда (из каталога lite-kit):

```sh
# station-max/lite-kit
sudo ./stop.sh
```

Затем удалите временные DNS-переопределения или верните прежнюю DNS-настройку роутера; если DNS раздавался по DHCP, восстановите её для всей сети.

## Этап 4. Получение root-доступа и установка rootd

К этому этапу сборка зафиксирована, OTA-lock включён. root нужен для установки `rootd` и постоянного выполнения команд; сам эксплойт работает через ADB.

### 4.1. Быстрая установка

```sh
bash scripts/quick-install.sh 192.168.1.149
```

Скрипт выполняет шаги 4.2–4.5 за один проход. Сначала он проверяет наличие `adb` и `python3`, доступность станции и сборку `PPR1.180610.011.5000000921`. Затем запускает `get-root.py` и `install.sh`; оба перед отправкой бинарника сверяют его контрольную сумму с `binaries/SHA256SUMS`. Если установщик выводит `WARN` про `/init`, скрипт останавливается до перезагрузки. Иначе перезагружает станцию, ждёт `sys.boot_completed=1` и проверяет, что SELinux в `Permissive`, `rootd` запустился и очередь принимает задания: последняя проверка — `run-root.sh "id"` с ожиданием `uid=0`.

Если набор уже установлен и работает, скрипт сообщает об этом и завершается без повторных записей; для переустановки добавьте `--force`. Подразделы 4.2–4.5 описывают те же действия вручную — на случай, если скрипт остановился и нужно понять, на каком шаге.

### 4.2. Шаг 1. Временный root-доступ

Убедитесь, что станция на сборке `5000000921`:

```sh
adb -s 192.168.1.149:5555 shell getprop ro.build.display.id
# ожидается PPR1.180610.011.5000000921
```

Затем на компьютере:

```sh
python3 scripts/get-root.py 192.168.1.149
```

Скрипт сверяет контрольную сумму `esc` с `binaries/SHA256SUMS`, передаёт его на станцию, выполняет девять записей через esc-flip (адрес `0x291352c` и область `0x13ed028`–`0x13ed044`), затем в одной сессии читает `/sys/fs/selinux/reject_unknown` и проверяет, что получен `uid=0`. Успех подтверждается строкой `УДАЛОСЬ: uid=0 в сессии, где сработал триггер`.

### 4.3. Шаг 2. Установка набора

В той же root-сессии (скрипт использует тот же read-триггер):

```sh
bash scripts/install.sh 192.168.1.149
```

`install.sh` передаёт на станцию `rootd`, `rootd.rc`, `rootup`, `enforce-up.sh`, `adbd-watchdog.sh` и `install_device.sh`; перед отправкой он сверяет контрольную сумму `rootd` с `binaries/SHA256SUMS`, затем запускает установщик в root-сессии. Установщик:

1. Кладёт `rootup`, `enforce-up.sh`, `adbd-watchdog.sh` в `/data/local/tmp/rootd`, создаёт там `rootup.out` и `/data/local/tmp/rootd.log` (`root:root 0644`) — их `rootd` открывает при загрузке ещё до перевода в Permissive; проверяет, что `esc` уже на станции (его загрузил `get-root.py`), и выставляет ему `root:root` и `0755`.
2. Перемонтирует `/odm` в режим записи. Бинарник кладётся рядом как `/odm/bin/rootd.new`, получает `root:root`, `0755` и метку `adbd_exec`, затем переименовывается в `/odm/bin/rootd` — `cp` поверх работающего файла даёт `ETXTBSY`, так как `init` держит его исполняемым; `rename` этого не задевает. Так же обновляется `/odm/etc/init/rootd.rc`. После этого сверяет `sha256` файла на станции с `/data/local/tmp/stage/rootd` и возвращает `/odm` в режим только для чтения.
3. Создаёт очередь `/data/local/tmp/rootq/{pending,running,results}` с правами `0700` и владельцем `shell:shell`.
4. Печатает `ls -laZ` для установленных путей и проверяет, упоминает ли `/init` каталог `/odm/etc/init`. В конце выводит `=== done rc=0 ===`; `install.sh` считает установку успешной только по этой строке, потому что `adb shell` не возвращает код удалённой команды, и дополнительно сверяет `sha256 /odm/bin/rootd` с локальным бинарником.

Если последняя проверка выводит `WARN`, init на этой прошивке может не подхватывать `/odm/etc/init/*.rc`; тогда `rootd` не запустится после перезагрузки. Не перезагружайте станцию, пока не выясните это: проверьте разбор rc в `/init` и журнал загрузки.

### 4.4. Шаг 3. Перезагрузка и проверка

```sh
adb -s 192.168.1.149:5555 reboot
# дождитесь возврата ADB; при необходимости adb connect 192.168.1.149:5555
```

После загрузки:

```sh
adb -s 192.168.1.149:5555 shell getprop ro.build.display.id   # сборка
adb -s 192.168.1.149:5555 shell getenforce                     # ожидается Permissive
adb -s 192.168.1.149:5555 shell cat /data/local/tmp/logs/enforce.log  # перевод в permissive
adb -s 192.168.1.149:5555 shell cat /data/local/tmp/rootd.log  # запуск демона
adb -s 192.168.1.149:5555 shell ls -laZ /data/local/tmp/rootq
```

`rootd` должен запуститься при `sys.boot_completed=1`, сначала выполнить `rootup` (перевод в permissive и запуск watchdog в фоне) и только затем начать следить за очередью. Ход перевода в permissive виден в `/data/local/tmp/logs/enforce.log`; если файла нет, стартовые команды не выполнились — смотрите `/data/local/tmp/rootd/rootup.out` и `/data/local/tmp/rootd.log`. Если ADB после перезагрузки не поднимается, watchdog не сработал или служба не стартовала — проверьте журнал и конфигурацию, не повторяйте установку вслепую.

### 4.5. Выполнение команд от root

```sh
bash scripts/run-root.sh "id"
```

Скрипт атомарно кладёт задание в `/data/local/tmp/rootq/pending`, ждёт результат в `results/` и печатает вывод. Команда выполняется `rootd` от UID 0. Запись в очередь позволяет выполнить произвольную команду от root, поэтому не расширяйте доступ к ней без необходимости.

### 4.6. Выключение lite-kit и проверка watchdog

Если lite-kit ещё работает, остановите его и уберите DNS-переопределения (как в 3.2). После этого перезагрузите станцию ещё раз и проверьте, что ADB вернулся, `getenforce` показывает `Permissive`, а `/data/local/tmp/rootd.log` пополняется: это проверяет, что `adbd-watchdog` держит ADB без помощи lite-kit.

Если lite-kit был выключен до Этапа 4, эта проверка уже произошла при перезагрузке в 4.4.

Если после перезагрузки ADB не поднялся, восстановите стенд (DNS-переопределения и `lite-kit/start.sh`), дождитесь синхронизации и разберите `/data/local/tmp/logs/adbd.log`.
